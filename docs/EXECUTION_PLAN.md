## 3. 首轮交付范围

先交付一个真实脑肿瘤分割模型的完整闭环：多序列病例 → 模型推理 → 原空间多类别 mask → 三视图叠加/体积统计 → 报告 → 医生确认；同时提供独立批量评估脚本与结果报告。

第一轮冻结新增阅片工具、3D 特效、LLM 报告、分子预测、生存预测和多模型融合。现有占位结果保留时必须清楚标注来源，不纳入真实模型实验。SQLite 可继续用于本地科研闭环；多人部署再安排权限、审计与数据库升级。

## 4. 优先级与任务顺序

### P0：建立可复现基线与坐标契约（预计 2–3 个工作日）

1. 盘点 GPU/显存、现有环境、数据版本、序列、标签、权重来源和许可；记录实际运行环境，不根据 requirements 文件推断已安装模型。
2. 建立独立后端/推理环境，核对核心依赖：radiomics_service 导入 scipy，但 requirements-core 未直接声明；测试另需 pytest/httpx。记录锁定版本和启动命令。
3. 统一 NIfTI affine、轴向、spacing 与坐标转换。当前 VIEW_AXIS 直接指定 axial=0，不能保证符合任意 NIfTI 的解剖方向；SimpleITK 数组与 spacing 顺序也需核对。保存原空间与模型空间的变换。
4. 以带非单位 spacing、轴翻转/置换及已知标志点的合成体积验证三视图、crosshair、探针、mask 对齐和 mm 测距；MRI 探针文字改为强度值。
5. 修正路径解析、预处理同名文件冲突和分析错误契约。模型预处理遵循权重配置，不能把现有全体积归一化结果直接当成所有模型的通用输入。
6. 合并遗留 reports 缓存/硬编码路径入口与真实病例报告入口；预测历史关联 MRI、模型及运行记录。重复分析使旧医生确认失效，并保存历史确认所对应的结果版本。

验收：基础服务可复现启动；合成影像坐标验证通过；错误不会生成成功预测/报告；重启后病例和报告可读。

### P1：选择一份兼容权重，先离线推理（预计 2–4 个工作日）

首选评估 nnU-Net v2 接入路径，前提是有来源可核验、任务匹配、许可允许且环境兼容的权重。已有可运行 MedNeXt 权重时可调整顺序，以最短实际可运行路径为准。框架安装成功不代表已有脑肿瘤权重。

- 使用 2–5 个有标签病例做通路验证，不作为最终性能结论。
- 明确 checkpoint、训练数据来源、通道顺序、模型配置、标签语义及输入预处理。nnU-Net 推理输入必须与训练输入格式及通道定义一致。
- 若选定权重需要 T1/T1ce/T2/FLAIR，扩展当前「取最新一份 MRI」结构为同一次检查的多序列；缺序列明确失败，不用复制单序列补齐。
- BaseSegmenter 扩展为结构化输入/输出：序列路径、输出目录、配置；返回 mask、标签映射、模型版本、运行记录。仅 segment(mri_path) 不足以支持多通道。
- 推理在独立进程/服务运行；先本地单 worker，提供 queued/running/succeeded/failed、超时、失败重试、避免重复任务及恢复规则。
- 保存 mask 时恢复原空间；检查 shape、affine、spacing、标签集合。临时文件验证通过后原子替换，避免坏上传覆盖已有有效 mask。

验收：真实权重离线产生可复现 mask；与源图空间一致；模型不可用时明确失败，不自动返回模拟结果。

### P2：打通产品闭环（预计 2–3 个工作日）

- 增加序列上传/映射与完整性提示；病例详情显示模型任务状态、耗时、失败原因。
- 分割来源区分 mock/uploaded/model；多类别颜色和语义根据版本化标签表映射。
- 从真实 mask 计算区域体积（体素数 × spacing 乘积，转换为 mL），同时保存模型版本及输入标识。
- 报告展示真实分割结论和来源；不把分割能力转换成未经校准的诊断概率/生存月份。
- 医生确认绑定具体结果版本；新增 MRI、替换 mask 或重新推理后要求重新确认。
- 补关键 API 和浏览器流程测试，替换前端「You did it!」模板测试；验证刷新、重复分析、异常和 PDF。
- Docker 持久化数据库、上传、推理产物；核对 CORS 与前端 API 地址，完成重建容器恢复验收。

验收：新病例从序列上传到真实叠加、报告、确认、PDF、重启恢复完整通过。

### P3：完成可审计的实验评估（预计 3–5 个工作日，可能与界面接入部分重叠）

1. 使用来源和授权清楚的带标签数据。公开挑战的 validation/test 标签可能隐藏；本地评估应从有标签数据划分独立留出集，或按官方允许的流程提交。
2. 先冻结患者级 train/validation/test 清单、随机种子、数据版本和标签映射；同一患者各序列/时间点不能跨集合。核查预训练权重是否见过拟评估病例；不清楚时披露重叠风险，不称作独立测试。
3. 按所选 BraTS 版本定义 WT/TC/ET，逐病例计算 Dice、HD95（mm）、体积误差、耗时、失败率和显存。IoU 可附列；AUC 不用于分割主任务。
4. 预先定义双空/单空区域的指标规则，HD95 无法定义时单列缺失与原因；失败病例计入分母，不只报告成功病例均值。
5. 报告样本量、均值/中位数、分布与患者级 bootstrap 置信区间；若比较模型，采用相同患者的配对分析。只有一个模型时报告性能，不宣称优于其他方法。
6. 输出逐病例 CSV、汇总 JSON、复现实验配置、环境版本、checkpoint 哈希、数据划分、运行日志、失败清单、最佳/中位/最差病例叠加图和 Markdown 报告。
7. 若以已有模型为基线做改进，先选一个可检验因素（如模型配置或后处理），在 validation 调整，冻结方案后一次性评估 test。不要同时更换数据、模型和预处理。

验收：另一环境按文档可重跑；每个结果可追溯到数据、权重、配置；留出集无已知患者泄漏；性能局限清楚。

## 5. 时间与完成标准

在兼容权重、可用 GPU 和有标签数据已就绪的前提下，首轮估计 9–15 个有效工作日。上述阶段为工时估计，部分可重叠，不能视为硬性截止承诺。若需要从零训练、申请数据或重新配准，另做资源和计算时长评估。

首轮完成必须同时具备：真实模型、原空间 mask、可用产品闭环、冻结的评估协议、逐病例与汇总结果、可复现环境和运行说明。接入成功但没有独立评估，或界面完整但返回占位数据，均未达到本轮目标。

首个实施批次建议只做 P0，并同时核验一份候选权重的可运行性。拿到首个可信 mask 后再扩展页面，以降低反复修改成本。

## 6. 后续任务的进入条件

- 分子分型：具备明确 IDH/MGMT/1p19q 等目标及病理标签，再安排分类评估与校准。
- 生存预测：具备随访时间、事件状态及删失信息，再建立生存基线与评估。
- TabICL/多模态融合：有任务匹配的临床字段、标签、样本量与患者划分；先比较单模态基线，再验证融合收益。
- LLM：结构化结果与报告模板稳定后接入，不代替模型评估。
