# 导师常见问题与答复

适用于 `BF-RC-20261021.1` 工程演示。回答仅覆盖当前代码与实际验证范围，不将原型描述为临床系统。

1. **为什么开发这套系统？**  为研究脑胶质瘤多序列 MRI 的数据管理、分割、定量和结果追溯流程，形成可复现的工程原型。它不替代医院影像系统或医生判断。
2. **与现有医疗影像软件有什么区别？**  现有 PACS/RIS 主要承担临床归档和工作流。本项目关注研究性 SegResNet 分割和病例—分析—报告关联；目前不是获批临床产品，也没有完整临床部署。
3. **PACS 与 Orthanc 是什么关系？**  PACS 是影像归档系统类别。Orthanc 是本项目隔离验证使用的开源 DICOM 归档服务，支持 DICOMweb 插件；当前 Stage 7 归档为空且与正式服务隔离。
4. **DICOM 与 NIfTI 有什么区别？**  DICOM 常以实例保存临床影像及检查元数据；NIfTI 常用于研究体数据和体素空间信息。转换可改变组织方式，但不会自动解决序列身份、患者来源或空间对齐问题。
5. **DICOMweb 做什么？**  通过 QIDO-RS 等接口查询 Study/Series/Instance，通过 WADO-RS 获取影像内容。访问仍受认证、来源授权和像素读取门控限制。
6. **Cornerstone3D 做什么？**  它是浏览器内影像体/切片显示与交互组件。PACS 查询、身份核验、访问控制和数据传输由其他模块负责。当前实际彩排的是对齐 NIfTI 工作站；真实 DICOM 像素阅片未通过。
7. **为什么需要四序列 MRI？**  T1c、T1n、T2w、FLAIR 提供互补组织对比，符合本模型输入约定。四个文件存在并不能证明它们来自同一检查或已配准。
8. **为什么要配准和重采样？**  分析时不同模态的体素需对应同一物理空间。要核对方向、affine、spacing、origin、覆盖范围，选择参考空间并应用空间变换；简单 resize 不会建立正确的解剖对应关系。
9. **UPENN 病例是否已通过审核？**  没有。636 个 DICOM 已解码并分别做过转换；当前仍等待人工隐私、序列身份和配准复核，未导入 Orthanc、未做 DICOMweb 像素读取、未运行该病例推理。
10. **SegResNet 从哪里来？**  项目调用 MONAI BraTS SegResNet 和其预训练权重；本 RC 没有训练新模型。演示报告展示了权重摘要，工程代码实现输入校验、运行编排和输出持久化。
11. **WT、TC、ET 分别是什么？**  当前代码按 BraTS 输出标签映射计算：WT 为标签 1/2/3，TC 为 1/3，ET 为 3。实际医学解释应以模型标签定义及医生审阅为准。
12. **体积怎么计算？**  对区域掩膜计数体素，再乘 NIfTI affine 三维线性变换矩阵行列式的绝对值，换算为毫升。空间单位或 affine 错误会影响结果，因此输入几何校验很重要。
13. **为什么采用分析运行记录/异步任务？**  影像推理耗时长，运行记录可表达排队、运行、成功或失败，并让输出绑定输入和模型版本。当前 RC 实测保存了一次成功运行；所有崩溃恢复和重试路径尚未在本轮完整验证。
14. **报告怎样关联模型结果？**  报告记录链接到分析运行 ID，展示模型修订、区域体积和工件摘要。RC 实测报告 ID 1 与成功运行 `f01f37f194ae4290ba51cb53e9aeebab` 关联，并在后端重启后可读取。
15. **分割是否代表诊断？**  不代表。分割只是模型输出；当前报告注明研究限制且医生复核为“待复核”，不能据此做诊疗决定。
16. **哪些算法是自行实现，哪些是复用？**  SegResNet 网络和预训练权重来自 MONAI/BraTS 生态；PACS/Orthanc、DICOMweb 和 Cornerstone 也依赖开源组件。项目自行实现数据门控、转换注册、任务/工件追踪、体积、报告关系和业务 UI。详细依赖版本见锁文件和镜像清单。
17. **模型性能如何？**  本次证明的是对指定工程样本成功执行推理并保存输出，不是准确率评估。没有以此报告灵敏度、Dice 或临床泛化性能；性能研究需要独立标注、数据划分和预先定义的实验方案。
18. **DICOM阅片现在能演示吗？**  当前不能演示真实 DICOM 像素。Edge 彩排验证了 NIfTI 三平面画布；UPENN 尚未获准导入，Stage 7 Orthanc 保持空档案。
19. **是否连接正式医院 PACS？**  否。RC PACS 配置独立且不可用，导入、像素读取与 AI bridge 都关闭；没有改正式 PACS 或病例 17/19。
20. **本地账户就代表医生认证吗？**  不是。本地账户角色用于原型访问控制，不验证执业资格，也不等同电子签名或正式身份系统。
21. **为什么使用 SQLite 和 Docker？**  SQLite 适用于本地单机原型，易于隔离和备份；Docker 固定服务依赖和运行边界。正式多人协作、可用性和监管部署仍需重新评估数据库、密钥和运维设计。
22. **备份和恢复验证到哪一步？**  本轮通过 SQLite online backup 备份 RC 数据库并检查完整性；E/C tracked diff 的反向检查及未跟踪文件哈希也通过。尚未进行主机/磁盘故障后的完整环境还原演练。
23. **系统何时可以临床使用？**  目前不具备临床使用结论。还缺少真实 DICOM 链路验收、人工影像审核、临床性能和风险验证、正式部署与权限审计等工作。
24. **下一步怎样做论文实验？**  先确定获准数据、纳排标准、患者级隔离划分、参考标注、指标及统计方案；冻结代码/模型版本并保存可追溯实验记录。不要把当前演示样本写成临床队列结果。
25. **LLM 报告、RAG 和多模态 MRI 做到哪一步？**  仅属未来研发方向，本 RC 没有可用接口或实测模型。本轮未启动相关模型或接入外部服务。
